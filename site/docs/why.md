# 为什么需要 kuul

## 需求真实，难在可控落地

- 超过半数企业已经部署多步骤 Agent，80% 报告获得了可衡量的回报（Anthropic《2026 State of AI Agents》）；
- Gartner 预测：到 2027 年，超过 40% 的 Agentic AI 项目会被取消；
- 企业最大的三个障碍是**集成（46%）、数据质量（42%）、变更管理（39%）**；
- 工具投毒攻击成功率最高达 72.8%（MCPTox）；员工私自部署的“影子 Agent”游离在 IT 治理之外。

::: tip 结论
这些问题没有一个能靠更强的模型解决，都要靠更稳、更可控的底座。
:::

## 严监管企业的四条铁律

银行、政府、电信、能源、医疗这类企业要求：

1. 数据不出企业；
2. 系统完全可审计；
3. 新组件要过安全合规流程；
4. 技术栈要与现有体系对齐。

监管还在收紧：国内的智能体实施意见要求三级决策权限，人工审批、权限分级和行为留痕成为硬要求；欧盟 AI Act 的透明度义务自 2026 年 8 月起适用。

现有选项都满足不了这些企业：

| 选项 | 问题 |
|---|---|
| SaaS / 云托管 | 数据出企业，锁定生态 |
| 直接用 OpenClaw / Hermes | 有安全事件史，默认权限宽松，技术栈不对齐 |
| 用框架自己写 | 每个团队都要重复造权限、审计、隔离的轮子，标准还不统一 |

企业需要的是**统一的底座**：模型接入与配额、身份权限、工具治理、审计都应该统一。这和当年从各写各的线程池走向统一应用服务器、走向 Kubernetes 是同一个逻辑。

## 开源 Agent OS 留下的空白

OpenClaw（Node.js）和 Hermes Agent（Python）定义了个人 Agent OS 的产品形态，但都从个人和小团队场景起步，共同留下五个空白：

1. 没有完整的企业治理：多租户 RBAC、SSO、审计、合规留证；
2. 安全是外挂的，不是内核能力：缺少技能签名、权限声明、最小授权和凭证托管；
3. 企业 IT 系统（ERP、CRM、CMDB）需要各家自己适配；
4. 以单机为主，缺少集群和高可用；
5. Java 生态缺位。

## Java 生态：有框架，没底座

62% 的企业已经在用 Java 构建 AI 功能。Spring AI、LangChain4j、AgentScope Java 让“写 Agent”这一层已经成形，但“跑 Agent”这一层几乎是空的。

| 支点 | 说明 |
|---|---|
| 部署即标准 | kuul 就是一个 Spring Boot 应用，IT 部门不需要学新东西 |
| LLM 接入复用 | 直接用 Spring AI |
| 运维工具链复用 | Nacos、Sentinel、SkyWalking、Arthas、Prometheus |
| 系统对接成本低 | Tool 可以直接调用企业现有的 Java 服务，不需要跨语言胶水 |
| 安全与合规现成 | Spring Security、OIDC、Vault，以及企业现有的代码审计和 SBOM 流程 |

## 安全：与 OpenClaw 反向设计

| 维度 | OpenClaw | kuul |
|---|---|---|
| 技能来源 | 开放市场，默认信任 | 注册、审核、签名后才能使用 |
| 权限 | 默认权限大 | 最小权限，按需放开 |
| 隔离 | 可选，靠外部加固 | 强制沙箱 |
| 凭证 | 常见明文配置 | 环境变量 / 密钥文件，扩展阶段对接 KMS / Vault |
| 注入与外泄 | 依赖模型自身判断 | Tool 输出隔离、外发限制、高风险动作需审批 |
| 审计 | 只有会话日志 | 全链路结构化审计，可接入 SIEM |

## 设计原则

1. **治理优先**：身份、权限、审计、隔离都是内核能力，第一天就具备。
2. **默认最小授权**：能力必须显式授予，默认拒绝。
3. **一切可审计**：关键动作写入结构化审计日志。
4. **确定性内核**：模型输出被视为不可信输入，高风险动作要经过策略引擎和人工审批。
5. **兼容开放标准**：SKILL.md、MCP、A2A、OpenTelemetry GenAI。
6. **Java 原生、Spring 友好**：标准 Spring Boot 工程，与企业现有工具链直接咬合。
7. **单机做扎实，架构不堵路**。

> 愿景：成为 Java 生态 Agent OS 层的事实标准，就像 Tomcat 之于 Web 应用，让每一家企业都能在自己的边界内，像管理服务一样管理 Agent。
